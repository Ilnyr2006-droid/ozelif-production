## Isolated outage and rollback, 2026-10-31

An isolated Ubuntu 24.04 container ran real systemd, Nginx, Node 22.23.1 and a separate PostgreSQL 16 with synthetic data. Two complete PostgreSQL stop/start cycles on a fixed port returned 200 → 503 → 200 without restarting the API process; requests during the outage returned within milliseconds. A second test through Nginx and systemd returned 200 → 503 → 200 with the service remaining active; the next cycle hit the configured Nginx 429 rate limit during its outage, so it is not evidence of a second gateway-level 503. A bounded pool acquisition and late-client release were added, with a regression test. However, timeout does not cancel the pending pool waiter: repeated stalled connections could accumulate queued waiters. This is an unresolved release blocker and requires a genuinely cancellable or bounded queue, plus an integration test. SQL remains limited by a 3-second statement timeout; this does not prove behavior for every network partition or a stalled transaction control statement.

The systemd/Nginx cycle switched the copied active API source to the API-only release: health 200, unauthorized evidence 401, authorized evidence 200. Making the new entrypoint unavailable made systemd report failure; switching to the previous copy restored active service, health 200 and evidence 404. The three source files for checkout, public catalog and CRM were byte-identical across releases. This does not prove complete checkout, catalog or admin end-to-end behavior: the isolated database only contains analytics-related tables, and no production or test order was created. A second isolated cycle edited the unit's absolute WorkingDirectory and ExecStart from old to new, simulated entrypoint failure, then restored the old absolute paths: systemd returned active and health 200. The exact production unit override and production configuration still require separate review. Do not apply test switch commands to production.

## Reproducible candidate source

The generator `scripts/order-evidence/build-release.py` accepts a separately obtained, secret-free snapshot of the current active release and an absent output directory. It rejects symlinks, selected secret/backup names and mismatches in the reviewed baseline `server/index.mjs`, `server/lib/db.mjs`, and package lock. It overlays only `server/lib/db.mjs`, the two evidence modules and a minimal route registration. It records SHA-256 and file modes for every output file. It does not authenticate every input baseline file; independently compare a full source manifest against the active release, and re-identify the active service before approval. Never run `npm ci` in production as part of this preparation.

Example on an isolated workstation, with a previously verified snapshot and dependencies installed from the same lockfile in a separate isolated directory:

```sh
python3 scripts/order-evidence/build-release.py --baseline /path/to/verified-active-snapshot --output /path/to/new-api-source
python3 scripts/order-evidence/build-release.py --baseline /path/to/verified-active-snapshot --output /path/to/rebuilt-api-source
cmp /path/to/new-api-source/SHA256SUMS.json /path/to/rebuilt-api-source/SHA256SUMS.json
```
