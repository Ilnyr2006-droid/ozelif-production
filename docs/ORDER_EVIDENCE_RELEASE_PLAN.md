# Два этапа выпуска аналитики заказов

Статус: подготовка и тесты; ни один этап не разрешён к выпуску этим документом. Не сливать PR и не менять production до отдельного разрешения владельца. Второй этап не является условием проверки первого, но его прототип не включать и не представлять как работающую сверку.

## 1. Защищённый API заказов

Область: только `GET /api/internal/direct/order-evidence` с отдельным Bearer-токеном, ограничением диапазона и нагрузки, read-only транзакцией и агрегатным JSON. Этап не требует миграций, не изменяет checkout, существующие источники заказов или клиентскую цель Метрики. Данные `utm_campaign` — неподтверждённый ввод клиента; CRM `paid` не доказывает банковский платёж. Любые подтверждённые CPA и ROAS остаются `null`; возможные расчёты по UTM и CRM должны явно содержать эти оговорки и не называться подтверждёнными.

Критерии готовности:

- Активный релиз и его исходники определены повторной read-only проверкой непосредственно перед выпуском; endpoint переносится отдельно на эту точную базу. Никаких замен checkout, каталога, админки, unrelated файлов и старого frontend из ветки PR.
- SQL проверен на отдельном PostgreSQL с актуальной копией схемы, без реальных персональных данных; уникальность заказов при повторных строках, периоды, статусы, валюты, ошибки и пустой результат проверены. Подтвердить доступность таблиц и нужных индексов в production через read-only анализ; отсутствие индекса или стоимость запроса при текущей нагрузке — блокер до решения и отдельного плана.
- Нет токена — 404, неверный токен — 401, корректный — только агрегаты; ошибочные параметры — 400, ошибка БД — безопасный 503. Проверены отсутствие PII, секретов, SQL и кеширования, тайм-аут и ограничение одновременных запросов; отдельный длинный случайный токен хранится только в защищённом окружении API и MCP. Настроить ограничения доступа и частоты на доверенной границе; не полагаться на лимит in-process как на общий лимит для нескольких процессов.
- Контракт фактического API проверен с фактическим локальным MCP в изолированной среде; `confirmedCpaRub`, `paidCpaRub`, `verifiedRoas` и `verifiedRevenueRub` отсутствуют либо `null`, если нет отдельного подтверждения источника, атрибуции и оплаты. Проверить отказоустойчивость при недоступном API.
- Повторно прошли серверные и frontend тесты, typecheck, lint и сборка; после подготовки релиза проверены read-only health, каталог, админка и маршрут заказа без создания заказов. После разрешённого выпуска проверить реальный endpoint с токеном и без него, на ограниченном периоде, без вывода секретов и без тестовых конверсий. Проверка живого MCP требует отдельного разрешения на его перезапуск.

Откат: до выпуска сохранить точный путь/артефакт активного API, конфигурацию сервиса и Nginx с правами доступа; проверить возможность возврата. При инциденте отключить маршрут или удалить отдельный токен в защищённой конфигурации (маршрут возвращает 404 после перезапуска), вернуть предыдущий артефакт API и перезапустить только по разрешённому плану. Отключить токен MCP; не трогать таблицы, заказы и существующие цели. Поскольку миграций нет, откат схемы не нужен. Нельзя заявлять проверку отката, пока переключение и возврат не проверены в изолированном окружении.

Read-only осмотр 31 октября 2026: активный каталог API `/opt/ozelif-api-releases/direct-feed-20261029.uCtOfL`; имеются индексы по `ad_attribution(entity_type, entity_id)`, `order_status_history(order_id, created_at, id)` и `metrika_purchase_outbox(order_id)`. Индекса с первым полем `orders.created_at` или выражением `utm_campaign` среди найденных нет. Существование других индексов не доказывает приемлемое время запроса; нужны оценка плана и реалистичная нагрузочная проверка. Изолированный PostgreSQL-тест использует временные фиктивные таблицы, а не копию актуальной схемы; требование выше пока не закрыто.

## 2. Подтверждение событий и рекламная атрибуция

Область, возможная реализация и границы доверия — `ORDER_GOAL_RECONCILIATION_DESIGN.md`. В настоящее время подготовлен только изолированный прототип; он не выдаёт разрешения на изменение checkout, баз данных, Метрики или включение серверной отправки.

Критерии готовности:

- На отдельном тестовом счётчике и тестовой БД доказано, что цель и непрозрачный идентификатор доступны в одной строке Logs API; проверены точный формат, период, задержки, полнота выгрузки, лимиты и права. Если нет — выбрать другой проверяемый механизм, не делать вид, что данные подтверждены.
- Идемпотентное создание заказа и единый канал отправки; протестированы параллельные запросы и вкладки, повторная выгрузка, отдельные дубли, потеря ответа и недоступный счётчик. Не отправлять автоматически заново после неопределённого результата. Технические статусы не смешивать с подтверждением в отчётах.
- Определены и реализованы отдельные доказательства: событие наблюдалось, связь с заказом, надёжная атрибуция рекламной кампании и подтверждённая оплата; одних UTM или ClientID недостаточно. Для каждого доказательства есть источник, период, срок действия и отрицательные тесты. Исторические заказы без фактической связи остаются неподтверждёнными.
- Непрозрачные идентификаторы не содержат PII; доступ к соответствию с заказом, выгрузкам и токенам ограничен. Проверены срок хранения, удаление/обезличивание, перехват и подделка браузерного параметра, неполная выгрузка и несовместимость структуры. MCP выдаёт только безопасные агрегаты.
- Подготовлены миграции и совместимый откат, проверены на отдельной копии схемы PostgreSQL с конкуренцией; отдельно протестирован переход с отключённым feature flag и без двойной отправки. Предоставлен план мониторинга и владелец отдельно разрешил включение.

Откат: выключить новый источник отправки и сверку согласно выбранной политике, не включая второй канал автоматически; при неизвестных запросах не повторять отправку. Вернуть прежнюю совместимую версию checkout/API, сохранить записи и схему на период отката, пока старая версия с ними совместима. Удаление столбцов или очистка данных — отдельное решение после проверки зависимостей и резервной копии. Продолжить явно маркировать старые и неподтверждённые события как неизвестные.

## Действия владельца перед первым этапом

Утвердить отдельное окно выпуска, доступ к защищённому хранению отдельного случайного Bearer-токена и конкретную процедуру переключения/отката после завершения проверки активного релиза и тестов. Не передавать токен в чат. До решения по второму этапу предоставить отдельный тестовый счётчик Метрики и разрешить испытания только на нём, если его ещё нет.
