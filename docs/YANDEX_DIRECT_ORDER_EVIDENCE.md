# OZELIF → Yandex Direct MCP: защищённая сводка заказов

Экспериментальная серверная интеграция для проверки заказов, без передачи персональных данных посетителей в ChatGPT.

## API

`GET /api/internal/direct/order-evidence?campaignId=715543180&dateFrom=2026-10-01&dateTo=2026-10-14`

Требует заголовок `Authorization: Bearer <secret>`. Если `OZELIF_MCP_ORDER_READ_TOKEN` отсутствует или короче 32 символов, endpoint возвращает 404.

Ответ содержит только агрегаты заказов, сохранённых с `utm_campaign`, точно равным переданному `campaignId`. Телефоны, контакты, ФИО, комментарии, адреса и ID отдельных покупателей **не возвращаются**. Даты относятся к времени создания заказа в часовом поясе Europe/Moscow, обе границы включительны; диапазон ограничен 92 календарными днями.

`createdOrders` включает отменённые заявки; `cancelledOrders` — текущий статус отмены, а `attributedOrders` равно `createdOrders` в рамках UTM-фильтра. `paidOrders` и `everPaidOrders` — не отменённые заказы с текущим или историческим статусом CRM `paid`; `currentlyPaidOrders` — заказы с текущим статусом `paid`. `paidRevenueRub` включает текущую сумму этих неотменённых заказов в валюте RUB; история изменения суммы и возвраты отдельно не учитываются. `nonRubPaidOrders` показывает, сколько заказов с CRM-статусом оплаты имеют другую или неизвестную валюту; при ненулевом значении рублёвая сумма не охватывает все оплаченные заказы. `purchaseOutboxSent` — число совпавших заказов со статусом outbox `sent`; это отдельный показатель, который может включать впоследствии отменённые заказы.

Внимание: фильтрация кампании по сохранённому `utm_campaign` является атрибуцией, заявленной URL-параметром, а не независимой проверкой источника клика. Ответ явно содержит `campaignAttributionVerified: false` и `attributionEvidence: client_supplied_utm_campaign_unverified`; он не доказывает CPA или ROAS кампании. `paid` отражает статус CRM, а не подтверждение платежа от эквайринга. `purchaseOutboxSent` означает статус отправки в нашей системе; **это не доказательство срабатывания цели 609951402 в Метрике**. `checkoutGoalVerified` и `goalEventMatched` всегда `false`: текущий клиентский `order_created` не передаёт идентификатор для поштучной корреляции.

`goalExists` и `goalActivityVerified` в ответе CRM равны `null`: этот источник не читает API Метрики. `orderGoalVerified` равен `false` до независимой поштучной сверки. Отдельная проверка API подтвердила цель 609951402 «Оформлен заказ» с условием `order_created`, два целевых визита и два достижения за 7 сентября — 20 октября 2026 года без выборки. Это не доказательство конкретных заказов; целевые визиты и достижения цели являются разными метриками. В PostgreSQL за этот период было три заказа `website_cart`; совпадение по датам и количеству не устанавливает связь с посещениями.

Токен Директа возвращал 403 при чтении Метрики; отдельный токен Метрики из защищённого хранилища успешно прочитал цель. При изменении прав проверить аккаунт, выдавший токен, доступ к счётчику и разрешение OAuth `metrika:read`. Не отправлять секрет в чат.

## Включение (только после ревью PR)

1. Подготовьте отдельный случайный ключ на сервере (пример команды: `openssl rand -hex 32`). Не помещайте его в Git или в диалог ChatGPT.
2. Сохраните секрет на сервере как `OZELIF_MCP_ORDER_READ_TOKEN` в приватном окружении сервиса API, а тот же ключ — в защищённом окружении MCP-клиента. Не используйте `ADMIN_SESSION_SECRET` и не переиспользуйте токен Яндекс Директа.
3. Убедитесь, что HTTPS-путь `/api/internal/direct/order-evidence` маршрутизируется Nginx к этому API. Запрос без ключа должен вернуть 401, а при отсутствии сервера-секрета — 404.
4. На стороне MCP установите `OZELIF_REPORT_CURRENCY=RUB` **только после** проверки валюты расходов в рекламном кабинете.
5. Протестируйте период, в котором известны заявки с UTM `utm_campaign` конкретной кампании. Если UTM не содержат числовой ID кампании, метод законно вернёт ноль и потребуется отдельная корректная схема связывания.
6. Проверка с настоящим API должна быть read-only, без включения рекламных записей.

## Проверки

API-тесту требуются фиктивные локальные `DATABASE_URL` и `ADMIN_SESSION_SECRET`, поскольку импорт маршрута загружает общую конфигурацию. `ORDER_EVIDENCE_TEST_DATABASE_URL=<адрес отдельной тестовой БД> node --test server/lib/marketing-order-evidence.postgres.node-test.mjs` проверяет SQL и HTTP на временных таблицах PostgreSQL, удаляемых при закрытии соединения. Тест допускает только локальную БД `evidence_test` на нестандартном порту; не направляйте его на production.

Не запускать клиентский скрипт отправки покупок в Метрику для этой задачи: он выполняет внешние события и не нужен для чтения.

## Необходимые дальнейшие доработки

- Поштучно сверять конкретные заказы и события цели из Logs API Метрики, без передачи клиентских персональных данных.
- Подтверждать оплату через платёжного провайдера (если бизнес требует подтверждённый ROAS, а не CRM-статус).
- Настроить мониторинг и лимиты доступности endpoint, журналировать только коды ошибок, не запросы/секреты.
